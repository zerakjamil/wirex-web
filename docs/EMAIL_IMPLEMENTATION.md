# SMTP and POP3 instructional model

## Implemented behavior

Server-PT exposes configurable SMTP submission on TCP port 25 and POP3 retrieval/deletion on TCP port 110. The server configuration sets a mail domain, toggles each service, and creates up to 100 credentialed local mailboxes. PC and Laptop Desktop > Email saves an account, submits a message, retrieves an inbox, and shows Inbox and Sent folders. A student can ask the server to delete a selected message after confirming; changing the selection cancels that confirmation. Deletion uses the incoming server, account credentials, and the simulated TCP path. The downloaded client Inbox copy remains available. Messages are delivered only to mailboxes on the configured local domain; an unknown recipient, bad credentials, a disabled service, blocked route/ACL, unavailable server, or unknown message ID returns a visible error.

SMTP sends a textual exchange inside the simulated TCP data stream: EHLO, AUTH PLAIN, MAIL FROM, RCPT TO, DATA, a bounded set of message headers, dot-stuffed body lines, the DATA terminator and QUIT. The server enforces command order, checks credentials and local mailboxes, rejects malformed or injected headers, and returns SMTP status lines. POP3 retrieval and deletion each keep one simulated TCP session open. The client sends one USER/PASS/STAT/LIST/UIDL command and receives its response before sending the next; retrieval follows UIDLs with one RETR per message and QUIT, while deletion follows the snapshot with DELE and QUIT. The server validates each command against session state and commits deletion only at QUIT; RSET clears pending marks in the protocol processor. Multiline responses use dot transparency, and the client verifies UIDLs before adding messages to its Inbox. The PDU inspector shows segment ports, flags, sequence numbers and text payload, including a warning for visible SMTP AUTH PLAIN and POP3 PASS credentials. The simulator carries session identity and routing metadata alongside those bytes.

All requests use the simulated IP, ARP, VLAN, routing, ACL, TCP handshake, segmentation, reassembly, acknowledgement, retransmission and connection-close paths. Store integration verifies Alice can submit through a 2911 router from one subnet to a Server-PT on another, and Bob can retrieve the delivered message from a third subnet. A routed ACL denial reports the ACL name, egress interface, source/destination addresses and TCP port in the transaction failure. A 60 KiB body regression crosses multiple TCP segments. SMTP persists successful messages on the server and the sender's Sent folder; POP3 copies mailbox messages into the client Inbox. Server-side deletion uses textual DELE/QUIT commands, validates the UIDL snapshot, commits only at QUIT and preserves the downloaded client Inbox copy. Successful and failed transactions are retained in the simulation state.

Workspace persistence validates email service and client settings, mailbox count and size limits, addresses, duplicate IDs and message sizes. Server mailbox capacity is 250 messages, each body is limited to 64 KiB, and a POP3 response is capped at 64 KiB. The end-to-end acceptance uses two PCs and one Server-PT on a shared switch, with a message sent by Alice and retrieved by Bob.

## Limits

SMTP implements an instructional command subset, not a complete RFC server: it supports one recipient, AUTH PLAIN, this client's EHLO/DATA flow and text bodies, without pipelining, SMTPUTF8 negotiation, MIME, attachments or extension parity. POP3 models one command/response per simulated TCP turn, but does not implement a raw socket daemon or complete RFC behavior. Mail is local-domain only: DNS MX lookup, external relaying, aliases, TLS and MIME are not implemented. AUTH PLAIN and POP3 PASS are not encrypted; credentials and messages are also stored in the local workspace in clear text. Use only isolated classroom credentials, never real accounts or sensitive data.

## Verification

- Seven SMTP and eight POP3 protocol tests cover command framing, authentication, order validation, status parsing, dot transparency, UIDL matching, DELE commit at QUIT, RSET rollback and malformed input rejection. Store/engine regressions capture the SMTP stream and POP3 LIST/UIDL, RETR and DELE streams on TCP, local delivery/retrieval/deletion, routed delivery/retrieval across three IPv4 subnets, a routed SMTP ACL denial with the exact blocked flow in its reason, and a body requiring TCP segmentation. Deletion tests confirm that a failed authentication, stale UIDL or unknown message leaves the server mailbox unchanged, while success removes the server copy only after QUIT and retains the downloaded Inbox copy. Browser coverage confirms changing the selected message cancels the pending delete confirmation.
- Workspace-schema tests cover valid email state and reject malformed or oversized settings.
- `e2e/email.spec.ts` verifies Server-PT setup, two local mailboxes, Alice sending to Bob, Bob retrieving and reading the message, confirming POP3 server deletion, retaining the downloaded Inbox copy, and showing the server mailbox count return to zero. The latest focused production-browser run passes 1/1; the POP3 inbox check took 9,710 ms, down from 17,174 ms before packet animation was accelerated. The store regression requires one-message retrieval to complete in fewer than 80 simulation ticks.
- On 2026-10-15, `rtk npm run check` passes 418 tests, TypeScript, optimized production build and a zero-advisory production dependency audit; lint reports zero errors and 28 existing warnings. The final `rtk npm test` also passes 418/418 with the stricter 80-tick POP3 budget. The full production-browser suite passes 27/27, including email and routing, DHCP, GRE, STP, SNMP, TFTP and voice flows. The rebuilt preview at `127.0.0.1:3005` returned HTTP 200 for the app and HTTP 403 for SQLite and Electron-build endpoints, and the listener is bound to loopback.

The feature is not evidence that the application matches Packet Tracer's full mail protocol implementation. Broader routing/ACL topologies and instructor acceptance remain release work; see `REPLACEMENT_GATES.md`.
