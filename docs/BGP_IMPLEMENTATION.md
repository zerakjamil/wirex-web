# BGP implementation (eBGP 2026-10-17; iBGP and TCP handshake 2026-10-18)

IPv4 BGP exchanges simulated TCP-handshake, OPEN, KEEPALIVE, UPDATE and NOTIFICATION packets, forms sessions between directly connected routers in different autonomous systems (eBGP) and inside one autonomous system (iBGP), propagates prefixes with AS-path loop prevention and installs learned routes that carry real traffic — `B` entries at distance 20 for eBGP and 200 for iBGP. This is still a reduced BGP model, not a full BGP-4 parity claim and not the complete replacement release gate.

## Student workflow

On a routing-capable device (a router, or a Layer 3 switch with `ip routing`) configure `router bgp <1-65535>`, then `bgp router-id <A.B.C.D>`, `neighbor <A.B.C.D> remote-as <1-65535>` and `network <A.B.C.D> [mask <M.M.M.M>]` statements; an omitted mask uses the classful default. A `remote-as` equal to the local AS configures an iBGP neighbor. `no neighbor <ip>` removes a peer, `no network` removes an announcement and `no router bgp <AS>` clears the process, the runtime and every learned `B` route. `clear ip bgp *` resets all peers to Idle (paths withdrawn, sessions reconverge on the next retry), which is the documented way to force recovery. Re-entering `router bgp` with a different AS is refused — the same convention the EIGRP model documents. Inspect with:

- `show ip bgp` — local networks (with a `(not in routing table)` marker when no connected subnet matches) and learned prefixes: next hop, metric, local preference, weight, AS path
- `show ip bgp summary` (or `show ip bgp neighbors`) — router identifier, local AS, table version, and per-neighbor state (including `Connect` while the transport handshake retries), message counters, up/down and prefixes received
- `show ip protocols` — the `Routing Protocol is "bgp <AS>"` section with the router ID and configured neighbors
- `show ip route` — learned entries as `B` with `[20/0]` for eBGP and `[200/0]` for iBGP routes
- `show running-config` — the whole `router bgp` block

## Packet and timer behavior

- Every session starts with the simulated TCP three-way handshake on port 179: the initiating peer sends SYN and retries every 5 simulated seconds while in Connect; a device that runs BGP and has a matching neighbor statement answers SYN-ACK; receiving SYN-ACK sends ACK plus the BGP OPEN. A device that runs BGP but has no neighbor statement for the source answers RST — the originator returns to Idle with the refusal recorded and keeps retrying every 5 seconds — and a device that does not run BGP stays silent. The handshake frames are ordinary PDUs labeled `TCP SYN` / `TCP SYN-ACK` / `TCP ACK` / `TCP RST` on port 179 in the layer-4 details.
- Sessions keepalive every 60 simulated seconds and a peer expires after a 180 second hold time; an OpenSent peer re-sends OPEN every 5 seconds. The reduced FSM is Idle → Connect → OpenSent → OpenConfirm → Established.
- Receiving an OPEN while OpenConfirm or Established performs a full re-open (learned paths cleared, OPEN and KEEPALIVE re-sent); a KEEPALIVE in OpenConfirm establishes the session and immediately pushes the full current table as UPDATEs. Hold expiry — only tracked while OpenConfirm or Established — and configuration removal reset the session and withdraw the peer's paths.
- Updates advertise the sender's full current best-path set. Toward eBGP peers the local AS is prepended and NEXT_HOP is rewritten to the sender's egress interface, and the receiver validates it against the receiving subnet. Toward iBGP peers the AS path is unchanged — including the empty path used for networks originated inside the AS — and relayed routes keep their learned NEXT_HOP, accepted even when it is outside the receiving subnet (the classic "next hop not reachable" teaching case). A peer's own AS in the AS_PATH causes the entry to be dropped (loop prevention), and iBGP-learned paths are not relayed to other iBGP peers (no route reflection) while they are advertised to eBGP peers with local-AS prepending. A remote-AS mismatch to the configured neighbor sends NOTIFICATION and resets the session. Entries arrive in chunks of at most 100 with the final chunk marked `complete`; incomplete multi-chunk updates merge per prefix. AS paths are capped at 64 hops and peers at 2,048 learned prefixes.
- Best-path selection is shortest AS_PATH, then an eBGP path over an iBGP path, then the lowest neighbor address. eBGP routes install at administrative distance 20 and iBGP routes at 200; neither overrides directly connected subnets. A `network` statement announces a prefix only while an operational connected subnet matches it.
- eBGP peering is link-local: the neighbor must be directly connected (TTL 1) and frames that cannot be routed are dropped by the engine, leaving the peer unestablished.
- BGP control traffic also rides operational GRE tunnels: the tunneled handshake/OPEN/KEEPALIVE/UPDATE follows underlay routing and ARP, and the peer processes it on its Tunnel interface.

The model is a documented simplification: no route reflectors or confederations, no capabilities negotiation, communities, MED, local preference or route policies, no IPv6 address families, no route dampening, and no BGP-relevant `show` breadth beyond the commands listed above.

## Evidence

- `src/simulator/bgp.test.ts` — ten packet-level tests: two-router establishment with CLI output (`show ip bgp`, `show ip bgp summary`); a real PC-to-PC echo reply over the learned route; a remote-AS mismatch that sends NOTIFICATION, blocks the routes and exposes reasons on both peers; `clear ip bgp *` reset with timer-driven reconvergence; link shutdown with hold-time expiry withdrawing the `B` route; a three-router chain verifying AS-path prepending, relay through an uninvolved transit router and loop prevention; the TCP handshake (SYN, SYN-ACK, ACK) visible in the PDU stream of a live session; an iBGP pair exchanging a route with an empty AS path and installing it at distance 200; a four-router case proving iBGP-learned routes are not relayed to other iBGP peers yet reach an eBGP peer with `65002 65001` prepending; and a TCP RST refusal from a device that runs BGP without a neighbor statement.
- E2E flow F13 configures `router bgp 65001`, an eBGP neighbor (`remote-as 65002`), an iBGP neighbor (`remote-as 65001`) and `network 10.0.0.0 mask 255.255.0.0` from the browser CLI and verifies `show ip bgp summary` (both neighbors), `show ip bgp`, `show ip protocols` and running-config output.
- Current whole-repository verification is recorded in `LAUNCH_READINESS.md` and `HANDOFF.md`: 546/546 unit tests, lint zero errors with the 28 existing warnings, the optimized build with zero production-dependency advisories, and 48 of 49 production-browser flows — every functional flow passes including F13, while the realtime scale case passed all functional assertions (8/8 pings, queue peak 2,132, clean drain, no warnings) and its wall-clock pacing bound flagged at 534 ms under host load against the unchanged 500 ms bound, matching the same-host A/B band (501–534 ms across builds; the previous commit measured 520–528 ms under identical load), so it is a machine-boundary artifact and the bound was not weakened.

## Remaining boundaries

Payloads are structured educational messages, not binary BGP-4 datagrams interoperating with real routers. Route policy attributes (communities, MED, local preference, weight), route reflectors and confederations, capabilities negotiation, IPv6 address families, route dampening and larger real-world AS-path behaviors are out of scope for this reduced model. Packet Tracer comparison has not been performed for BGP output. The routing row in `REPLACEMENT_GATES.md` remains open.
